# Loop Report — make the delta legible

Output a **Loop Report** designed to be the user's review surface, since they did not watch each phase:

- Branch name and the path to `loop-state.md`.
- The Uroboros version the run ran on (the `UROBOROS:` line in `loop-state.md`), with every version a resume ran on.
- The spec-kit version detected at the start of the run (the `SPEC-KIT:` line in `loop-state.md`) and the contract version the plugin was verified against.
- **Models and guides:** per role (orchestrator, reviewer, refuter, implementer, verifier), the release it ran on and the model guide applied or `none` (the `MODEL GUIDES` record in `loop-state.md`), plus every model mismatch the Model check caught and every report the Contract check sent back for repair, and how each was resolved.
- The run's size (small or standard) and the round cap it set, or the `--rounds` value that replaced it.
- Per phase: inferences caught, findings refuted, questions answered, risks accepted, gate result — and, for implement, the gate baseline (`GATE BASELINE`: green, `unavailable`, or what was already failing and what the user decided about it), how many `proof` findings were fixed, and the convergence outcome per round (converged, or the appended task ids).
- **The delta, in plain language:** for each phase, the files changed and a human-readable summary of *what substantively changed and why* — not just "updated spec.md". For implement, include `git diff --stat <BASE TREE> <the last ROUND TREE>` (Working-tree snapshots; without snapshots, `git diff --stat`) plus a plain-English walkthrough of what the code now does differently.
- **Verification:** first every scenario not verified, with its reason — and, if the user chose so, the UI left unverified; then each scenario in plain words with its outcome per round and one line of evidence; the browser used; and the `VERIFY COMMANDS`, as the commands to run the product and check it by hand.
- **Seen outside this feature:** each item the verifier observed outside the scenarios, and each finding the refuter refuted as already there before the run (`not-this-run`), in plain words, with its source and whether it touches a file the run changed. The run did not fix them.
- **Files the verification created** (untracked), for the user to keep or delete.
- **Candidate rules to encode (the loop improving the loop):** scan the run's findings and deviations in `loop-state.md` for **recurring classes** — the same kind of inference or defect flagged across multiple phases or rounds (e.g. non-measurable criteria appearing three times, the same missing-scope pattern, a convention the implementer kept violating). For each recurring class, propose one concrete rule and where to encode it — the project constitution, `CLAUDE.md`, or a skill — so future runs stop producing that class of finding at the source. Propose only; the user decides what to adopt. One-off findings are not candidates.
- The full DECISION LOG (every question and the user's answer), per the Question protocol: each entry describes the decision in plain words first, with the finding/assumption id only as a trailing trace tag — the user never saw the ids during the run. Folds derived from an earlier decision (`→ derived from`) are listed with the decision they came from, and facts folded from the repository (`→ discoverable`) with the file they came from.
- **Left out of this feature:** every minor case and every exhausted-cap item the user chose to leave out, in plain words — the behavior there is unspecified on purpose.
- **Refuted findings:** every other finding or risk the refuter refuted (`→ refuted`), in plain words, with its reason and proof, so the user can reopen any of them.
- **Assumption ledger** (only when the run used a question-suppressing mode — `--auto` / `--only-business`): every assumption from the ASSUMPTION LOG, described in plain words with its `A<n>` id as a trailing tag, with its rationale and where it landed in the artifacts, presented as the run's **audit surface** — these are the decisions the user delegated and must now review. If any assumption looks consequential enough that a default run would have made it a first-batch question, say so explicitly. Assumptions marked `skipped — red` (a gate check, or a `proof` finding, dropped under `--auto`), `baseline — red` (a failure already there before the run, left out of the gate under `--auto`), `skipped — repeated` (a finding or risk that came back unchanged and was skipped) and `unverified` (a design phase that advanced on an exhausted explicit `--rounds` cap under `--auto`) go first, in that order, each in its own block, as the highest-priority review: the gate or the reviewer never passed them. For each `skipped — red` and `baseline — red`, quote the failing output.
- **Standing decisions.** List, in plain words, this run's decisions that could bind beyond this feature (product or behavior decisions, not one-off details), then ask one `AskUserQuestion`: *Add none* / *Add all listed* / the numbers to add, written by the user (any other answer adds none). Append the chosen ones to `.uroboros/decisions.md` (SKILL.md, Standing decisions). Under `--auto`, do not ask or write: show the list for the user to add by hand.
- An explicit list of what is **left uncommitted** for the user to commit per their GitFlow.
- **Declined hooks:** if `HOOKS: unreadable` was recorded, say first that no spec-kit hook was checked in this run, quote the parser error, and tell the user to fix the file and run its mandatory hooks by hand. Then every optional spec-kit hook the run declined (`DECLINED HOOKS` in `loop-state.md`), each with the command to run it by hand (e.g. `/speckit-git-commit`) — the run never commits or runs optional hooks on the user's behalf.

Do not commit anything. The point is that the user can read this report and the diff and actually understand what the loop built.
