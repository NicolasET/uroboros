# Loop Report — make the delta legible

Output a **Loop Report** designed to be the user's review surface, since they did not watch each step. It is printed in the chat, where the user's own words may be quoted from the private record; a copy written to disk (a part's `loop-report.md`) restates them instead (hard rule 9).

- **First line:** `complete`, or `complete — <n> scenarios not verified` when the run closed with scenarios nobody could run (verify protocol, V4).
- Branch name and the path to `loop-state.md`.
- **The idea, item by item:** each `I<n>` of `IDEA ITEMS` in the user's words and where it ended — the acceptance criteria that build it, the Out of scope line and the answer that put it there, or the part that carries it — and each `GROWTH:` line.
- The Uroboros version the run ran on (the `UROBOROS:` line in `loop-state.md`), with every version a resume ran on.
- **Models and guides:** per role (orchestrator, reviewer, refuter, implementer, verifier), the release it ran on and the model guide applied or `none` (the `MODEL GUIDES` record in `loop-state.md`), plus every model mismatch the Model check caught and every report the Contract check sent back for repair, and how each was resolved.
- The run's size (small, medium or large), the signal that set it and who set it, what that size ran, and the round cap it set, or the `--rounds` value that replaced it. A size that changed mid-run, with what showed it.
- Per phase and round: inferences caught, items the refuter answered, questions answered, defects mitigated, risks accepted, gate result — and, for the build rounds, how the implementers ran (each wave from `### Waves` and its groups, or one implementer), the gate baseline (`GATE BASELINE`: green, `unavailable`, `no gate`, or what was already failing and what the user decided about it), each kind of check recorded as `none` and where the run looked for it, how many `proof` findings were fixed, each flaky check (implement protocol, Flaky checks) with what was decided, the review rules read (`REVIEW RULES`), each judging source restored after a build step (`### Judging sources restored`) — the file, whether the implementer's report named the change, and `git show <PRE TREE>:<path>` to recover the discarded version, since a change no report names may be the user's own — and each thing the implementer declared as not asked for (`### Unrequested (declared)`) with what was decided about it.
- **The delta, in plain language:** for each phase, the files changed and a human-readable summary of *what substantively changed and why* — not just "updated goal.md". For the build rounds, include `git diff --stat <BASE TREE> <the last ROUND TREE>` (Working-tree snapshots; without snapshots, `git diff --stat`) plus a plain-English walkthrough of what the code now does differently.
- **Verification:** first every scenario not verified, with its reason and whether the user chose to leave it or nothing local could supply it, and the `not-run` probes by reason with their count; then each scenario in plain words with its outcome per round and one line of evidence; then the probes: how many per criterion passed, each one that failed and how it was fixed, and each `open` behavior with what was decided; the browser used; and the `VERIFY COMMANDS`, as the commands to run the product and check it by hand.
- **Observed in what the run changed** (verify protocol, V3): each `O<n>` in plain words — fixed, with what the next verification saw; left for a later feature, with the answer or assumption that left it; or answered from the record.
- **Seen outside this feature:** each item the verifier observed outside the scenarios that touches no file the run changed, each probe that failed the same way before the run (`base: fails too`), and each finding the refuter refuted as already there before the run (`not-this-run`), in plain words, with its source and whether it touches a file the run changed. The run did not fix them.
- **Files the verification created** (untracked), for the user to keep or delete.
- **Candidate rules to encode (the loop improving the loop):** scan the run's findings and deviations in `loop-state.md` for **recurring classes** — the same kind of inference or defect flagged two or more times, across phases or rounds (e.g. non-measurable criteria appearing three times, the same missing-scope pattern, a convention the implementer kept violating). For each recurring class, propose one general rule as **trigger** (what in a diff makes it apply: files, symbols or a kind of change), **check** (what to verify) and **origin** (`seen <feature>, <date>` and what happened), with one sentence on why, and where to encode it — the project's `REVIEW.md` when a diff can trigger it (every implement review reads it — implement protocol, Review rules; the trigger, check and origin are this plugin's form inside a free-form file), `CLAUDE.md` or `AGENTS.md` when it applies to all work, or a skill — so future runs stop producing that class of finding at the source. Read those files first and leave out a rule they already state. Never propose a rule from an environment failure, a transient error, or a dead end the run backed out of. Propose only; the user decides what to adopt. One-off findings are not candidates.
- **Review rules to prune:** each rule in the project's `REVIEW.md` files whose trigger names a file, symbol or command the project no longer has, or that another rule repeats, with why. Propose only.
- The full DECISION LOG (every question and the user's answer), per the question protocol: each entry describes the decision in plain words first, with the finding/assumption id only as a trailing trace tag — the user never saw the ids during the run. Folds derived from an earlier decision (`→ derived from`) are listed with the decision they came from, and items the record answered (`→ refuted`, `decided` or `discoverable`) with the decision or file they came from.
- **Left out of this feature:** every minor case, every point the review raised (step D) and every exhausted-cap item the user chose to leave out, in plain words — the behavior there is unspecified on purpose.
- **Kept on "I don't know":** every list item the user answered "I don't know" (question protocol), in plain words, with what it was left as, so the user can still decide it.
- **Answered from the record:** every other item the refuter refuted — at intake, in a review, from the implementer or the verifier (`→ refuted`) — in plain words, with its reason and proof, and every defect mitigated without a question (`→ mitigated`) with its fix, so the user can reopen any of them.
- **Assumption ledger** (only when the run used a question-suppressing mode — `--auto` / `--only-business`): every assumption from the ASSUMPTION LOG, described in plain words with its `A<n>` id as a trailing tag, with its rationale and where it landed in the artifacts, presented as the run's **audit surface** — these are the decisions the user delegated and must now review. If any assumption looks consequential enough that a default run would have made it a first-batch question, say so explicitly. Assumptions marked `not-run` (a scenario left unverified under `--auto`), `skipped — red` (a gate check, or a `proof` finding, dropped under `--auto`), `baseline — red` (a failure already there before the run, left out of the gate under `--auto`), `flaky` (a check that failed only sometimes, left out of the gate under `--auto`), `no gate` (a project with no check to run, continued without one under `--auto`), `skipped — repeated` (a finding or risk that came back unchanged and was skipped) and `unverified` (`goal` or `plan` advanced on an exhausted explicit `--rounds` cap under `--auto`) go first, in that order, each in its own block, as the highest-priority review: the gate or the reviewer never passed them. For each `skipped — red`, `baseline — red` and `flaky`, quote the failing output.
- **Earlier decisions this run changed** (question protocol, Earlier features): each decision of an earlier feature that this run's work changed, in plain words — what that feature decided and what this run decided instead — and each one this run applied without a question, with the feature it came from.
- **Parts** (parts protocol; only when the run had them): after the main part's report, per part — its status, session, worktree, branch and state file, and its own Loop Report from `<dir>/loop-report.md` under its own heading; for a `stopped` part, where it stopped and why. Then the parts left as future runs and what each waits for; **the files more than one part changed** (`git -C <worktree> status --porcelain` per part, intersected) — the parts were split as independent, so each shared file is a merge to do by hand; and how to bring the parts together: commit each in its worktree, merge the branches, then `git worktree remove <path>`.
- **Project notes** (intake protocol, Project records): each entry of `.uroboros/project-notes.md` this run added, changed or removed, and why.
- **Glossary** (intake protocol, Project records): each entry of `.uroboros/glossary.md` this run added or changed.
- An explicit list of what is **left uncommitted** for the user to commit per their GitFlow.

Do not commit anything. The point is that the user can read this report and the diff and actually understand what the loop built.
