# Implement protocol — the build rounds

Read before the first implementer dispatch, and for a change asked after the run closes.

In the build rounds the maker is a dedicated subagent — several at once under `--parallel=N` when the work divides (Waves) — so it can run on a different model/effort than the orchestrator. The rest of each round (A2 gate, B review, C parse, D relay, E advance) is the loop protocol's.

## Step A — the implementer

1. **The implementer's model and effort** were settled at the start of the run (model protocol). If none is recorded, apply that protocol now, once: never dispatch the implementer on a choice the user did not make in this run.
2. **Base and gate baseline — before the first implementer dispatch.** Take `BASE TREE` (loop protocol, Working-tree snapshots). Discover and record the gate commands (step A2), run them on this untouched tree, and record `GATE BASELINE: <BASE TREE> — pass`, or each failing command with the failing tests its output names.
   - **No command:** when A2 finds no check at all, ask one question per the question protocol — also under `--only-business`. Say where you looked and why it matters: with nothing to run, the gate passes without proving anything, and only the reviewer and the verifier check the code. Options: *Continue with the reviewer and the verifier as the only proof* (a `D<n>`, marked `no gate`) / *Stop the run*. Commands the user writes instead become the recorded gate. *(Under `--auto`: continue, as an `A<n>` marked `no gate`.)* A run that continues records `GATE BASELINE: no gate`.
   - **Already red:** ask one question per the question protocol — also under `--only-business`, since the answer changes what the feature covers. Say what fails before any change — and, for a check the re-run showed flaky (Flaky checks), that it fails only sometimes — and why it matters: the gate cannot turn green while it fails. Options: *Fix them as part of this feature* (a `D<n>`; the implementer's dispatch carries them as work to do) / *Leave them out of the gate for this run* (a `D<n>`, marked `baseline — red`; every other check must still pass, and a new failure in the same command still counts) / *Stop the run*. *(Under `--auto`: leave them out, as an `A<n>` marked `baseline — red`.)*
   - **Resuming** an implement that had already started (code on disk): no baseline can be taken; record `GATE BASELINE: unavailable` and keep any recorded `BASE TREE`.
   - **Base drift** — here and on every resume. When `BASE BRANCH` names a branch, list what it has that this branch does not: `git log --name-only --format= HEAD..<name>` on the local ref. Never fetch, pull or rebase. If any listed file is one `goal.md` or `plan.md` names, or in the changed-file list, ask per the question protocol: the branch the feature started from has moved and changed these files, which this run has not seen — *Continue on the current base* / *Stop so you can update the branch yourself* (the run stops; Failure handling). *(Under `--auto`: continue, recorded as `A<n>`.)* If none is, record the list. While the list is not empty, pass it with the branch name as `BASE DRIFT:` to the implementer and the reviewer.
   - **Judging sources.** Record `JUDGING SOURCES` in `loop-state.md` as git pathspecs: the files that say what done is and how it is judged — every feature directory (`.uroboros/`, and `specs/` where features from before 1.0.0 live), `':(glob)**/REVIEW.md'`, `':(glob)**/CLAUDE.md'` and `':(glob)**/AGENTS.md'` — but not `':(exclude).uroboros/active-run.json'`, which the Stop hook writes while you wait. They change only through you — a fold, an added criterion (loop protocol, The build rounds); a fold that lands in one is yours, never the implementer's — and are checked after every implementer dispatch (item 4). A run resumed without the line records it now.
3. Plan the waves (Waves, below). Take `PRE TREE` (loop protocol, Working-tree snapshots) before every implementer dispatch of the run — this one, every re-dispatch, a fold, a fix, a wave. Dispatch `uroboros-implementer` with the chosen model and effort passed on the Agent call — once, with every criterion, when there are no waves; otherwise as Waves says — and wait for its `IMPLEMENTER-REPORT` (hard rule 7). In its prompt put: `INSTRUCTIONS: ${CLAUDE_PLUGIN_ROOT}/references/implementer-instructions.md` as the first line, `GOAL_FILE`, `PLAN_FILE` on a large run, `STATE_FILE`, `EARLIER_FEATURES` (if any), the `DECISION LOG`, `JUDGING_SOURCES` (item 2), on a re-dispatch the fixes and answers to fold, and — only if one applies — the implementer section of the guide for its resolved release as a verbatim `MODEL GUIDE:` block (model protocol). Every re-dispatch below carries the same block. Give every criterion to a dispatch and never tell one to leave a criterion to the verifier: the verifier is an independent check, never a substitute for the work (implementer instructions, item 4).
4. When its `IMPLEMENTER-REPORT` arrives, take `ROUND TREE <n>` first (loop protocol, Working-tree snapshots; after a wave, Waves, item 4). Then run the Model check on its `model:` line and the Contract check.
   - **Judging sources untouched.** Run `git diff --name-status <PRE TREE> <ROUND TREE n> -- <JUDGING SOURCES>`, leaving out `STATE_FILE` and the files this dispatch's criteria name as ones to change (without snapshots: `git status --porcelain` and `git diff --stat` before and after the dispatch, as verify V2 does). Then read `git diff <PRE TREE> <ROUND TREE n> -- <STATE_FILE>`: every changed line must be one you wrote since `PRE TREE` — the dispatch line, a restated decision, a check or repair record. Any other modified or deleted file (`M`, `D`), and any other line of the state file, is restored without a question, in every mode — from `git show <PRE TREE>:<path>`, re-applying your own lines — and logged under `### Judging sources restored` with the round, `PRE TREE` (the tree that keeps the discarded text) and whether the report's `files_changed` names it. When it does, the next dispatch tells the implementer the change was not its to make (implementer instructions, item 8). An added file (`A`) is only logged there.
   - **Log deviations:** append every deviation the implementer reports in `notes` to `loop-state.md` under this phase's `### Deviations` (one line each, with the round number). Deviations forced by reality are exactly what the Loop Report's candidate rules are mined from — do not let them evaporate with the subagent's context.
   - **Log the gate and the shared code it touched, and its red-first lines:** append each `gate_touched` entry under this phase's `### Gate touched`, each `shared_touched` entry under `### Shared code touched` and each `red_first` entry under `### Red first` (with the round number). The reviewer checks the run's diff against the first, weighs what else uses the second, and cites the third as evidence.
   - **Log what it declares as not asked for:** append each `unrequested` entry under this phase's `### Unrequested (declared)` (with the round number). The reviewer judges each one against the run's diff (reviewer instructions, Unrequested changes): a thing nobody asked for is a decision, a text written for something that was asked for is a value the run chose.
   - If `status: BLOCKED`, it hit a product/design ambiguity: give each `blocked_on` item a run-global `B<n>` (question protocol), let the record answer first (question protocol) — a refuted item goes into the re-dispatch as its proof says — and relay the rest to the user via `AskUserQuestion` per the question protocol — items that turn on the same point are one question (its `current:` paraphrased as what the code says today, ids only as trailing tags), record the answers in the DECISION LOG + `loop-state.md`, and **re-dispatch** the implementer (same chosen model/effort) with the answers to continue. Repeat until `status: DONE`. *(When the run mode suppresses the question — `--auto` always, `--only-business` for technical items — resolve the `blocked_on` item via the assumption mechanism instead: record `A<n>` in the ASSUMPTION LOG and re-dispatch with that resolution.)*

Then proceed to **A2** (you run the gate: the project's checks) and **B** (dispatch the reviewer) exactly as written in the loop protocol.

## Waves — several implementers at once

Under `--parallel=N` (N of 2 or more), the first build round runs several implementers at the same time, in the same working tree, when the work divides into groups that share no file. Without the flag there are no waves, since each dispatch reads the feature's artifacts again: in the testbed's implement eval (0.25.0), a wave of three groups of two tasks each cost 48% more and saved no time. Waves are only for step A's first pass and its `BLOCKED` re-dispatches; a fold, a red-gate fix and a verification fix are always one dispatch.

1. **Plan.** On a large run a **group** is a `G<n>` of the plan's Work order, with the files its `expects:` lists. Without a plan, a group is the acceptance criteria joined by the existing files you expect them to change, read from `goal.md` and the code: criteria that share a file are one group. Two groups can run beside each other when they name no file in common and neither needs the other (`after:` in the plan). A group whose files you cannot tell, or that names a dependency manifest or lockfile or a build, lint, type or test configuration, runs beside none. Walk the groups in order: a group joins the current wave when it can run beside every group already in it and the wave holds fewer than N; otherwise it starts the next wave — with a plan; without one there is a single wave, and a group that does not fit it goes to the dispatch after it. A wave left with one group is not a wave. Everything outside the waves goes, in order, to one dispatch at its place: before the first wave, between two, after the last. When no wave holds two groups, there are no waves: one dispatch gets everything. Record the plan under `### Waves` in `loop-state.md`: each wave, each group with its criteria and files, and the work of each dispatch between them — or `none`.
2. **Gate before each wave.** Before a wave, unless the gate already ran on this tree (the gate baseline), run the gate commands (step A2) and record the result. Red: one dispatch fixes it, with the failing output as a gate failure (step D), before the wave starts. Still red: there are no more waves — the work left goes to one dispatch, and A2 and the review go on as written.
3. **Dispatch.** Send every group of the wave in one message, one Agent call each, each with its `DISPATCH OPEN` line (loop protocol, Open dispatches) and the prompt of step A, item 3, plus `WAVE:` — its group and criteria, the existing files it may edit, and the groups running beside it with their files. Wait for every report before anything else (hard rule 7). A call refused because the session's concurrent-subagent limit is reached is not retried: its group waits for the next wave.
4. **Read the reports** one by one, as step A, item 4, says — its `ROUND TREE` taken once, when the last report arrives, and its judging-source check run once for the wave against the wave's `PRE TREE` — logging each entry with the round and its group (`r1 G2`). Ask the wave's `BLOCKED` items in one batch, then re-dispatch each blocked group with its answers, together, as the same wave. A criterion a group left in `tasks_remaining` because it needs a file outside its own goes to the dispatch that follows the wave — the one the plan puts there, or one of its own when the plan goes straight to another wave.
5. **Overlap.** A file in two reports of one wave, or one a group changed outside its own, is logged under `### Deviations`, naming the groups; the reviewer weighs it in its risk pass.


## The fold (step D) in the build rounds

You do not hand-edit the code yourself. Instead, **re-dispatch the implementer** (same model and effort) with the user's answers to the reviewer's findings and any gate failures — `weight: proof` findings included, each with its one fix — and ask it to bring every mention of each changed concept in line across the code and tests (step D, sweep), so all code is written by the strong maker. Log any new deviations, touched checks and touched shared code from its report and take the next `ROUND TREE`, as in step A, item 4. Then re-run the gate and re-dispatch the reviewer. Loop until CLEAN-with-evidence + green gate (round cap and repeated items per step D), then verify (verify protocol).

## Flaky checks

When a gate command fails, run the same recorded command once more on the same tree, unchanged — only to tell a flaky check from a broken one; the second result never turns the gate green. A test that failed in one run and not in the other is **flaky**; a command whose output names no tests is flaky as a whole when one run failed and the other passed. Flaky is red. Record both outputs with the gate result. A result recorded `on tree <id>` is not run again on a resume of the same tree.

- **A flaky check the run neither added nor changed** (its test is not in the run's diff) gets the *Already red* question of step A, item 2, saying it fails only sometimes, with both outputs; its *Leave them out* is marked `flaky`.
- **One the run added or changed** goes to the implementer as a gate failure (step D) with both outputs: the fix removes its cause (implementer instructions, item 7, says what does not count as one). It counts as fixed when the gate passes twice on the same tree. Still flaky after that fix, ask per the question protocol, with both outputs in plain words: *Delete the test* (a `D<n>` with the reason) / *Leave it out of the gate for this run* (a `D<n>` marked `flaky`; every other check must still pass, and a new failure in the same command still counts) / *Stop the run*. "I don't know" leaves it out. *(Under `--auto`: leave it out, as an `A<n>` marked `flaky` — step D's two rounds in a row.)*

## Review rules — the project's `REVIEW.md`

The project's own review rules reach the reviewer as they were before the run, so no change of the run rewrites what reviews it. Before the first review of the build rounds, and again when the changed-file list reaches a folder not yet covered, collect the files Claude Code's Code Review reads (code.claude.com/docs/en/code-review-customize):

- `REVIEW.md` at the project root;
- the files its lines that hold only `@<name>` include — a file beside it at the root, or `@.claude/skills/<folder>/SKILL.md` — at most eight, one level (an `@` line in an included file stays plain text);
- the `REVIEW.md` of each folder above a file in the changed-file list, except in or below a folder whose whole name, in any case, is `test`, `tests`, `__tests__`, `testdata`, `fixtures`, `__fixtures__`, `golden`, `corpus`, `snapshots`, `__snapshots__`, `example`, `examples`, `sample`, `samples`, `demo`, `demos`, `generated`, `vendor`, `third_party`, `third-party`, `thirdparty`, `node_modules`, `bower_components`, `external`, `extern`, `deps`, `godeps`, `pods`, `carthage`, `site-packages` or `contrib`.

Code Review reads the included and folder files only from a protected branch, so that a pull request cannot change them; a run gets the same protection by taking every file from `BASE TREE` (`git show <BASE TREE>:<path>`), never from the working tree. A file `BASE TREE` lacks is not read: a `REVIEW.md` the run creates or edits governs the next run, not this one. Write them, each under a `## <path>` heading, to `$(git rev-parse --git-path uroboros/review-rules.md)` and pass that absolute path as `REVIEW_RULES:` to the reviewer on implement (step B) and to the refuter with it. Record `REVIEW RULES: <paths, or none>` in `loop-state.md`. With none, pass no `REVIEW_RULES`. Without snapshots, use the working-tree files and record that they were.

## Resuming the build rounds

When the resume check picks up a run whose build rounds had already started (code exists on disk), continue at the recorded round. A wave left open is dispatched again per the loop protocol's Open dispatches, and the waves still to run are planned again from the groups no report covers. The recorded `BASE TREE` still defines the run's diff; if none was recorded, or it is gone, follow the snapshot fallback (loop protocol, Working-tree snapshots).

## After the run closes

A change the user asks for in this session after the Final report — a fix, an adjustment, one more thing — is never made by hand: the feature's code is written by the implementer and judged by the checkers, as before. Treat the request as a resume:

1. Write the message to the private record (hard rule 9), set the marker back to `"active"` with `relaunches` at 0, and check stale results (loop protocol) and base drift (step A, item 2), since the user may have edited or committed since the report.
2. Fold what the message changes into the artifacts as step D does. A change to a recorded decision is asked first (question protocol, The user's messages); a new thing it asks for is a new `I<n>`, once the question of the loop protocol's *A criterion that appears mid-run* confirms it.
3. Reopen the build rounds: the implementer, the gate, a review of that fold (`FOLDS`, `FOLD_DIFF`) and verification. Round numbers go on from the last one; the round cap counts from one.
4. Close again (loop protocol, Closing the run) and produce the Loop Report again, updated.

A request that is another feature — it does not fit this feature's goal condition — is not folded in: say so, and that it needs its own run.
