# Implement protocol — how step A and the fold differ

For the **implement** phase only, the maker is a dedicated subagent — several at once under `--parallel=N` when `tasks.md` allows it (Waves) — so it can run on a different model/effort than the orchestrator. Everything else in the loop (A2 gate, B review, C parse, D relay, E advance) is unchanged.

## Step A (implement)

1. **BLOCKING — settle the implementer's model/effort per the Model/effort protocol.** If `--implementer=<model>:<effort>` was given, that is the user's answer — record it and skip the question. Otherwise ask, and do not dispatch the implementer until the user has answered *in this run* (under `--auto` the choice was already settled at the start of the run). Record the choice in `loop-state.md`.
2. **Base and gate baseline — before the first implementer dispatch.** Take `BASE TREE` (Working-tree snapshots). Discover and record the gate commands (step A2), run them on this untouched tree, and record `GATE BASELINE: <BASE TREE> — pass`, or each failing command with the failing tests its output names.
   - **Already red:** ask one question per the Question protocol — also under `--only-business`, since the answer changes what the feature covers. Say what fails before any change and why it matters: the gate cannot turn green while it fails. Options: *Fix them as part of this feature* (a `D<n>`; the implementer's dispatch carries them as work to do) / *Leave them out of the gate for this run* (a `D<n>`, marked `baseline — red`; every other check must still pass, and a new failure in the same command still counts) / *Stop the run*. *(Under `--auto`: leave them out, as an `A<n>` marked `baseline — red`.)*
   - **Resuming** an implement that had already started (code on disk): no baseline can be taken; record `GATE BASELINE: unavailable` and keep any recorded `BASE TREE`.
   - **Base drift** — here and on every resume. When `BASE BRANCH` names a branch, list what it has that this branch does not: `git log --name-only --format= HEAD..<name>` on the local ref. Never fetch, pull or rebase. If any listed file is one the plan, `tasks.md` or `goal.md` names, or in the changed-file list, ask per the Question protocol: the branch the feature started from has moved and changed these files, which this run has not seen — *Continue on the current base* / *Stop so you can update the branch yourself* (the run stops; Failure handling). *(Under `--auto`: continue, recorded as `A<n>`.)* If none is, record the list. While the list is not empty, pass it with the branch name as `BASE DRIFT:` to the implementer and the reviewer.
3. Plan the waves (Waves, below). Dispatch the `uroboros-implementer-<effort>` variant of the chosen effort with the chosen model passed explicitly on the Agent call — once, with every task, when there are no waves; otherwise as Waves says — and wait for its `IMPLEMENTER-REPORT` (hard rule 7). In its prompt put: `INSTRUCTIONS: ${CLAUDE_PLUGIN_ROOT}/references/implementer-instructions.md` as the first line, `FEATURE_DIR`, the paths to `spec.md`/`plan.md`/`tasks.md` (+ data-model/contracts if present), `STATE_FILE`, `STANDING_DECISIONS` (if the file exists), the `DECISION LOG`, and — only if one applies — the implementer section of the guide for its resolved release as a verbatim `MODEL GUIDE:` block (Model/effort protocol). Every re-dispatch below carries the same block. Give every task to a dispatch and never tell one to skip a task — a validation task such as running `quickstart.md` included: the verifier is an independent check, never a substitute for a task (implementer instructions, item 4).
4. Read its `IMPLEMENTER-REPORT`. Run the Model check on its `model:` line and the Contract check first. Then take `ROUND TREE <n>` (Working-tree snapshots; after a wave, Waves, item 4).
   - **Log deviations:** append every deviation the implementer reports in `notes` to `loop-state.md` under this phase's `### Deviations` (one line each, with the round number). Deviations forced by reality are exactly what the Loop Report's candidate rules are mined from — do not let them evaporate with the subagent's context.
   - **Log the gate and the shared code it touched, and its red-first lines:** append each `gate_touched` entry under this phase's `### Gate touched`, each `shared_touched` entry under `### Shared code touched` and each `red_first` entry under `### Red first` (with the round number). The reviewer checks the run's diff against the first, weighs what else uses the second, and cites the third as evidence.
   - If `status: BLOCKED`, it hit a product/design ambiguity: give each `blocked_on` item a run-global `B<n>` (Question protocol), let the record answer first (Question protocol) — a refuted item goes into the re-dispatch as its proof says — and relay the rest to the user via `AskUserQuestion` per the Question protocol — items that turn on the same point are one question (its `current:` paraphrased as what the code says today, ids only as trailing tags), record the answers in the DECISION LOG + `loop-state.md`, and **re-dispatch** the implementer (same chosen model/effort) with the answers to continue. Repeat until `status: DONE`. *(When the run mode suppresses the question — `--auto` always, `--only-business` for technical items — resolve the `blocked_on` item via the assumption mechanism instead: record `A<n>` in the ASSUMPTION LOG and re-dispatch with that resolution.)*

Then proceed to **A2** (you run the gate: tests/lint/typecheck) and **B** (dispatch the reviewer) exactly as written in the loop.

## Waves — several implementers at once

Spec-kit's tasks template builds Setup and Foundational first and then lets the user stories proceed in parallel, one developer each (its "Parallel Team Strategy"). Under `--parallel=N` (N of 2 or more), implement does the same when `tasks.md` allows it: one implementer per story, at the same time, in the same working tree. Without the flag there are no waves, since each dispatch reads the feature's artifacts again: in the testbed's implement eval (0.25.0), a wave of three two-task stories cost 48% more and saved no time. Waves are only for step A's first pass and its `BLOCKED` re-dispatches; a fold, a red-gate fix, convergence tasks and a verification fix are always one dispatch.

1. **Plan.** A **group** is one user-story phase of `tasks.md` (`## Phase N: User Story k`) with the files its tasks name. Two groups can run beside each other when they name no file in common and neither depends on the other — in the `Dependencies & Execution Order` section or in a task; a `tasks.md` without that section has no waves. A group whose tasks name no file, or that names a dependency manifest or lockfile or a build, lint, type or test configuration, runs beside none. Walk the user-story phases in `tasks.md` order: a story joins the current wave when it can run beside every group already in it and the wave holds fewer than N; otherwise it starts the next wave. A wave left with one group is not a wave. Everything outside the waves — Setup, Foundational, a story left alone, Polish — goes, in `tasks.md` order, to one dispatch at its place: before the first wave, between two, after the last. When no wave holds two groups, there are no waves: one dispatch gets every task. Record the plan under `### Waves` in `loop-state.md`: each wave, each group with its task ids and files, and the tasks of each dispatch between them — or `none`.
2. **Gate before each wave.** Before a wave, unless the gate already ran on this tree (the gate baseline), run the gate commands (step A2) and record the result. Red: one dispatch fixes it, with the failing output as a gate failure (step D), before the wave starts. Still red: there are no more waves — the tasks left go to one dispatch, and A2 and the review go on as written.
3. **Dispatch.** Send every group of the wave in one message, one Agent call each, each with its `DISPATCH OPEN` line (the command's Active run) and the prompt of step A, item 3, plus `WAVE:` — its task ids, the existing files it may edit, and the groups running beside it with their files. Wait for every report before anything else (hard rule 7). A call refused because the session's concurrent-subagent limit is reached is not retried: its group waits for the next wave.
4. **Read the reports** one by one, as step A, item 4, says, logging each entry with the round and its group (`r1 US2`). Mark each `tasks_done` id `[X]` in `tasks.md`: implementers in a wave leave it to you. Ask the wave's `BLOCKED` items in one batch, then re-dispatch each blocked group with its answers, together, as the same wave. Take the `ROUND TREE` once every report is read. A task a group left in `tasks_remaining` because it needs a file outside its own goes to the dispatch that follows the wave — the one the plan puts there, or one of its own when the plan goes straight to another wave.
5. **Overlap.** A file in two reports of one wave, or one a group changed outside its own, is logged under `### Deviations`, naming the groups; the reviewer weighs it in its risk pass.

In goal mode, round 1 uses waves too under the same flag (goal protocol, G4, item 1). A group is the acceptance criteria joined by the existing files you expect them to change, read from `goal.md` and the code: criteria that share a file are one group, and a criterion whose files you cannot tell goes to the dispatch after the wave. There is one wave, and no Setup, Foundational or Polish.

## The fold (step D) for implement

You do not hand-edit the code yourself. Instead, **re-dispatch the implementer** (same variant and model) with the user's answers to the reviewer's findings and any gate failures — `weight: proof` findings included, each with its one fix — and ask it to bring every mention of each changed concept in line across the code and tests (step D, sweep), so all code is written by the strong maker. Log any new deviations, touched checks and touched shared code from its report and take the next `ROUND TREE`, as in step 4. Then re-run the gate and re-dispatch the reviewer. Loop until CLEAN-with-evidence + green gate (round cap and repeated items per step D), then run the convergence gate and verification below.

## The convergence gate, then verification (closes the phase)

CLEAN plus a green gate proves the written code is right; it does not prove nothing is **missing**. `speckit-converge` (spec-kit ≥ 0.11.2; optional per the compatibility check) proves that: it assesses the code against spec/plan/tasks and either appends the unbuilt work as `## Phase N: Convergence` tasks at the end of `tasks.md` (ids continue from the last `T###`, each with a source-ref such as `FR-003`, `US1/AC2`, `plan: …`, `Constitution II`) or leaves the file byte-for-byte untouched and reports **Converged**. It never edits code, spec or plan.

After CLEAN-with-evidence + green gate:

1. Invoke the `speckit-converge` skill inline (drive its hook directives per the hook policy).
2. **Converged** → record `CONVERGE: converged` under this phase in `loop-state.md`, then read `${CLAUDE_PLUGIN_ROOT}/references/verify-protocol.md` and verify; the phase closes (step E) when verification does.
3. **Tasks appended** → record the appended task ids and source-refs under this phase. A task whose gap type is `(unrequested)` flags code nobody asked for, and keeping or removing it is a product decision, so it never goes to the implementer as it is: once the record has answered first (Question protocol), ask per the Question protocol — what the code does today, why it matters — with the options *Keep it* (add a `## Clarifications` entry to `spec.md` citing the `D<n>`, so the next converge reads it as intent instead of appending the task again, and mark the task done) / *Remove it* (the implementer removes the code). *(When the run mode suppresses the question, resolve it via the assumption mechanism.)* Then re-dispatch the implementer (same chosen model/effort) with exactly the tasks left to do; re-run the gate; re-dispatch the reviewer with those tasks and the files they changed as its `FOLDS` (step B); then run converge again. Each pass counts as a round against the cap; if the cap is exhausted with tasks still being appended, follow the command's failure handling.
4. `speckit-converge` not installed → skip the gate, record `CONVERGE: skipped (skill not installed)`, and verify (verify protocol) on CLEAN + green gate.

Convergence tasks are sourced by construction (each traces to a spec/plan/constitution ref), so they raise no user question by themselves — except `(unrequested)` ones, asked in step 3; the reviewer audits their implementation like any other task.

## Resuming implement

When the resume check picks up a run whose implement phase had already started (code exists on disk), run `speckit-converge` **before** the first implementer dispatch so `tasks.md` reflects what the code already does, record the outcome, then continue at the recorded round. A wave left open is dispatched again per the command's Active run, and the waves still to run are planned again from the tasks left unchecked. The recorded `BASE TREE` still defines the run's diff; if none was recorded, or it is gone, follow the snapshot fallback (Working-tree snapshots).
