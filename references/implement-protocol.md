# Implement protocol — how step A and the fold differ

For the **implement** phase only, the maker is a dedicated subagent so it can run on a different model/effort than the orchestrator. Everything else in the loop (A2 gate, B review, C parse, D relay, E advance) is unchanged.

## Step A (implement)

1. **BLOCKING — settle the implementer's model/effort per the Model/effort protocol.** If `--implementer=<model>:<effort>` was given, that is the user's answer — record it and skip the question. Otherwise ask, and do not dispatch the implementer until the user has answered *in this run* (under `--auto` the choice was already settled at the start of the run). Record the choice in `loop-state.md`.
2. **Base and gate baseline — before the first implementer dispatch.** Take `BASE TREE` (Working-tree snapshots). Discover and record the gate commands (step A2), run them on this untouched tree, and record `GATE BASELINE: <BASE TREE> — pass`, or each failing command with the failing tests its output names.
   - **Already red:** ask one question per the Question protocol — also under `--only-business`, since the answer changes what the feature covers. Say what fails before any change and why it matters: the gate cannot turn green while it fails. Options: *Fix them as part of this feature* (a `D<n>`; the implementer's dispatch carries them as work to do) / *Leave them out of the gate for this run* (a `D<n>`, marked `baseline — red`; every other check must still pass, and a new failure in the same command still counts) / *Stop the run*. *(Under `--auto`: leave them out, as an `A<n>` marked `baseline — red`.)*
   - **Resuming** an implement that had already started (code on disk): no baseline can be taken; record `GATE BASELINE: unavailable` and keep any recorded `BASE TREE`.
3. Dispatch the `uroboros-implementer-<effort>` variant of the chosen effort with the chosen model passed explicitly on the Agent call, and wait for its `IMPLEMENTER-REPORT` (hard rule 7). In its prompt put: `INSTRUCTIONS: ${CLAUDE_PLUGIN_ROOT}/references/implementer-instructions.md` as the first line, `FEATURE_DIR`, the paths to `spec.md`/`plan.md`/`tasks.md` (+ data-model/contracts if present), `STATE_FILE`, `STANDING_DECISIONS` (if the file exists), the `DECISION LOG`, and — only if one applies — the implementer section of the guide for its resolved release as a verbatim `MODEL GUIDE:` block (Model/effort protocol). Every re-dispatch below carries the same block.
4. Read its `IMPLEMENTER-REPORT`. Run the Model check on its `model:` line first. Then take `ROUND TREE <n>` (Working-tree snapshots).
   - **Log deviations:** append every deviation the implementer reports in `notes` to `loop-state.md` under this phase's `### Deviations` (one line each, with the round number). Deviations forced by reality are exactly what the Loop Report's candidate rules are mined from — do not let them evaporate with the subagent's context.
   - **Log the gate and the shared code it touched:** append each `gate_touched` entry under this phase's `### Gate touched` and each `shared_touched` entry under `### Shared code touched` (with the round number). The reviewer checks the run's diff against the first and weighs what else uses the second.
   - If `status: BLOCKED`, it hit a product/design ambiguity: give each `blocked_on` item a run-global `B<n>` (Question protocol) and relay it to the user via `AskUserQuestion` per the Question protocol — items that turn on the same point are one question (its `current:` paraphrased as what the code says today, ids only as trailing tags), record the answers in the DECISION LOG + `loop-state.md`, and **re-dispatch** the implementer (same chosen model/effort) with the answers to continue. Repeat until `status: DONE`. *(When the run mode suppresses the question — `--auto` always, `--only-business` for technical items — resolve the `blocked_on` item via the assumption mechanism instead: record `A<n>` in the ASSUMPTION LOG and re-dispatch with that resolution.)*

Then proceed to **A2** (you run the gate: tests/lint/typecheck) and **B** (dispatch the reviewer) exactly as written in the loop.

## The fold (step D) for implement

You do not hand-edit the code yourself. Instead, **re-dispatch the implementer** (same variant and model) with the user's answers to the reviewer's findings and any gate failures — `weight: proof` findings included, each with its one fix — and ask it to bring every mention of each changed concept in line across the code and tests (step D, sweep), so all code is written by the strong maker. Log any new deviations, touched checks and touched shared code from its report and take the next `ROUND TREE`, as in step 4. Then re-run the gate and re-dispatch the reviewer. Loop until CLEAN-with-evidence + green gate (round cap and repeated items per step D), then run the convergence gate and verification below.

## The convergence gate, then verification (closes the phase)

CLEAN plus a green gate proves the written code is right; it does not prove nothing is **missing**. `speckit-converge` (spec-kit ≥ 0.11.2; optional per the compatibility check) proves that: it assesses the code against spec/plan/tasks and either appends the unbuilt work as `## Phase N: Convergence` tasks at the end of `tasks.md` (ids continue from the last `T###`, each with a source-ref such as `FR-003`, `US1/AC2`, `plan: …`, `Constitution II`) or leaves the file byte-for-byte untouched and reports **Converged**. It never edits code, spec or plan.

After CLEAN-with-evidence + green gate:

1. Invoke the `speckit-converge` skill inline (drive its hook directives per the hook policy).
2. **Converged** → record `CONVERGE: converged` under this phase in `loop-state.md`, then read `${CLAUDE_PLUGIN_ROOT}/references/verify-protocol.md` and verify; the phase closes (step E) when verification does.
3. **Tasks appended** → record the appended task ids and source-refs under this phase. A task whose gap type is `(unrequested)` flags code nobody asked for, and keeping or removing it is a product decision, so it never goes to the implementer as it is: ask per the Question protocol — what the code does today, why it matters — with the options *Keep it* (add a `## Clarifications` entry to `spec.md` citing the `D<n>`, so the next converge reads it as intent instead of appending the task again, and mark the task done) / *Remove it* (the implementer removes the code). *(When the run mode suppresses the question, resolve it via the assumption mechanism.)* Then re-dispatch the implementer (same chosen model/effort) with exactly the tasks left to do; re-run the gate; re-dispatch the reviewer with those tasks and the files they changed as its `FOLDS` (step B); then run converge again. Each pass counts as a round against the cap; if the cap is exhausted with tasks still being appended, follow the command's failure handling.
4. `speckit-converge` not installed → skip the gate, record `CONVERGE: skipped (skill not installed)`, and verify (verify protocol) on CLEAN + green gate.

Convergence tasks are sourced by construction (each traces to a spec/plan/constitution ref), so they raise no user question by themselves — except `(unrequested)` ones, asked in step 3; the reviewer audits their implementation like any other task.

## Resuming implement

When the resume check picks up a run whose implement phase had already started (code exists on disk), run `speckit-converge` **before** the first implementer dispatch so `tasks.md` reflects what the code already does, record the outcome, then continue at the recorded round. The recorded `BASE TREE` still defines the run's diff; if none was recorded, or it is gone, follow the snapshot fallback (Working-tree snapshots).
