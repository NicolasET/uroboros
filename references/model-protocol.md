# Model/effort protocol — who runs on what, and how each report is checked

Read before the first model choice is settled, and again on every resume.

## Model/effort protocol

The reviewer and the implementer run on a model + effort the user chooses at runtime. A choice given by flag (`--reviewer=` / `--implementer=`) IS the user's choice — record it and do not ask. The choices no flag gives are asked **once, at the very start of the run** — right after parsing the flags, before intake (on a resume, right after restoring the recorded state) — in one blocking `AskUserQuestion` call that holds, for each choice, **two separate questions** (up to four in all): question 1 = the model family (options: Fable, Opus, Sonnet — each described as the latest release of that family — plus free-form "Other"; never put version numbers in the options, they go stale); question 2 = the effort (options: low, medium, high, xhigh; `max` is accepted via "Other" — the question holds four options). Never combine model and effort into one question's options (question protocol, No option is recommended).

**How a choice is dispatched.** Each role is one agent — `uroboros-reviewer`, `uroboros-implementer`, `uroboros-verifier` (plugin-scoped name, e.g. `uroboros:uroboros-reviewer`) — that carries no instructions of its own. On every Agent call pass the chosen family alias (`fable`, `opus`, `sonnet`, `haiku`) as the call's `model` — it resolves to the latest release of that family — and the chosen effort as its `effort`, and make the first line of the prompt `INSTRUCTIONS: ${CLAUDE_PLUGIN_ROOT}/references/reviewer-instructions.md` (or `implementer-instructions.md`, `verifier-instructions.md`). If this session's Agent tool has no `effort` parameter (Claude Code before 2.1.292), stop before the first dispatch and say which version the plugin needs; never dispatch on an agent's own effort instead.

- **An effort that does not exist** (anything but low, medium, high, xhigh, max — via "Other" or a flag): ask again, naming the efforts that exist. *(Under `--auto`: it is asked in the call at the start, as if the flag were missing.)*
- **An exact version** (e.g. "Opus 5"): if it is the latest release of its family per the model list in your environment context, record it and dispatch the family alias. Otherwise the alias would run a different release than the one named — ask one question per the question protocol: run on that family's latest release (name it) or choose another family. *(Under `--auto`: use the latest release and record `A<n>`.)*

- **Reviewer:** its answer governs every reviewer dispatch of the run — do not re-ask per dispatch. **Per-phase mappings are allowed:** if the user's answer (typically via "Other") assigns different models/efforts to different phases — e.g. "Fable xhigh for plan and implement reviews, Sonnet high for the rest" — record the mapping and dispatch each review with the model/effort mapped to its phase.
- **Refuter:** runs on the reviewer's choice (per-phase mapping included) unless `--refuter=<model>:<effort>` was given; never asked. It is dispatched as `uroboros-reviewer` on its model and effort with `INSTRUCTIONS: ${CLAUDE_PLUGIN_ROOT}/references/refuter-instructions.md` as the first line. Record which choice it uses.
- **Verifier:** runs on the reviewer's choice for implement unless `--verifier=<model>:<effort>` was given; never asked. It is dispatched as `uroboros-verifier` with `INSTRUCTIONS: ${CLAUDE_PLUGIN_ROOT}/references/verifier-instructions.md` as the first line. In the headless fallback below it runs on its own frontmatter (`fable`, high), covered by the reviewer's `A<n>`. Record which choice it uses.
- **Implementer:** one choice per run; every implementer of a wave runs on it.
- **Under `--auto`** the call at the start is the only `AskUserQuestion` the run makes.
- **When `AskUserQuestion` is unavailable** (e.g. a headless `-p` session): dispatch the reviewer and the implementer without a model or effort override (their frontmatter: `fable` high and `opus` xhigh), recorded as `A<n>`.
- Write the answers into the intake draft; the intake protocol copies them to `loop-state.md`.
- Record every choice in the DECISION LOG and `loop-state.md`. On a resume, re-confirm the recorded choice instead of silently reusing it (in `--auto`, reuse it and note the reuse in the log; a choice not yet recorded is asked at the start of the resume, as above; a part session's first start re-confirms nothing — parts protocol, P4; a relaunch by the Stop hook or a compaction, in the session that owns the run, is not a new start and re-confirms nothing). If a dispatch is due and no choice is recorded, apply the protocol now (once) — never substitute a model of your own outside the assumption mechanism.

**Model guides.** A model release sometimes ships with its own prompting guidance. The plugin carries it curated per exact release in `${CLAUDE_PLUGIN_ROOT}/references/model-guides/<family>-<version>.md` (e.g. `opus-5.5.md`), with one section per role: `## Orchestrator`, `## Reviewer`, `## Implementer` (and `## Refuter` or `## Verifier` when the guide has advice for that role).

- **Subagents.** Once a subagent's choice is settled, resolve its family alias to the exact release it runs on — the latest release of that family per the model list in your environment context. If `<family>-<version>.md` exists for that release, paste its section for the role, verbatim, as a `MODEL GUIDE:` block into every dispatch of that agent. A guide for any other release of the family is never applied. If the release cannot be resolved, or no guide exists for it, dispatch without one.
- **Yourself.** At the start of the run (and of a resume), do the same for the model you are running on: if a guide exists for your exact release, read its `## Orchestrator` section and follow it for the whole run.
- **Record** under `MODEL GUIDES` in the DECISION LOG and `loop-state.md`, per role (orchestrator, reviewer, refuter, implementer, verifier): the resolved release and the guide applied, or `none` — noting when a guide exists only for another release of the family. Re-resolve on a resume; a new release may have shipped.
- **Precedence.** A guide never overrides the Hard rules, this protocol, the question protocol, or a return contract. On a conflict the plugin rule wins; note the conflict in `loop-state.md`.

**Model check.** Every subagent report carries a `model:` line with the exact model it ran on. If it differs from the release the alias resolved to — ignoring a context-window suffix such as `[1m]` — that dispatch did not run on the chosen model (e.g. its safeguards rerouted it to an older one): do not use the report yet — ask via `AskUserQuestion`, per the question protocol, whether to accept this dispatch's result or re-dispatch it. *(Under `--auto`: discard the report and re-dispatch once; if the mismatch repeats, stop and report — never assume past it.)* Record every mismatch and its resolution in `loop-state.md`.

**Contract check.** After the Model check, check every report against the output block of its role file. It breaks the contract when the block or a required field is missing — an implementer's `unrequested` included: a report without that line has not declared `none`; when `status: CLEAN` comes without an `evidence` block; when that block leaves out a criterion — on goal, plan and implement, any `AC-<n>`; on goal, and on an implement review that carries `GOAL_REVIEW: pending`, also any `I<n>` — or is empty; or when a `refuted` result has no `reason` or no `proof`. A broken report is not used. Repair it once, asking only for what is missing: with `SendMessage` to the same agent when this session has that tool, otherwise with a fresh dispatch of the same role, inputs and model plus a `REPAIR:` line naming what was missing. If the repaired report still breaks the contract, dispatch the role fresh once more; if that report breaks it too, stop and report, in every mode. Record each repair in `loop-state.md`.
