# Question protocol — how the run asks, and what it never asks twice

Read before the first question of the run, and again on every resume.

## Question protocol — every question is self-contained

Every question you ask — at intake, when relaying findings/risks or `BLOCKED` items — stands on its own (hard rule 8) and follows these rules:

- **The record answers first.** No question about the product or its design reaches the user before the refuter has tried to answer it from the record: the questions of an intake round, a review's findings and risks (step C), the implementer's `BLOCKED` items, the verifier's `open` probes and the defects it observed in what the run changed (verify protocol, V3). Send each batch once, before asking it, to the refuter (model protocol, Refuter), waited for (hard rule 7), with `PHASE` (`intake` until the feature has its folder), `RUN_MODE`, `STATE_FILE` (`.uroboros/intake.md` during intake), `PRIVATE_RECORD` (hard rule 9), `EARLIER_FEATURES` when there are any, the artifact paths, `RUN_DIFF` on implement, the DECISION LOG, and `FINDINGS:` each item with its run-global id — a review's items verbatim, every other as you would ask it: the decision, what is there today, the options. Run the Model check and the Contract check on its report. An item it returns `refuted` is not asked; log it as `<id> → refuted (<reason>): <proof>`:
  - `decided` or `discoverable` — fold the answer its proof cites where the item points (on implement, the implementer does it in the code on its next dispatch; a fold that lands in a judging source — implement protocol, step A, item 2 — is yours); the next review round verifies it like any fold.
  - `unreachable` or `no-outcome` — nothing to fold.
  - `not-this-run` — the Loop Report lists it under *Seen outside this feature*.

  `corroborated` and `inconclusive` items are asked; an item without a result counts as inconclusive. List each refuted item, in plain words with its source, where the user looks next — the shared-understanding check at intake, and the summary of step E after each review and each round — so the user can reopen it. Never sent, always asked: a question about the run rather than the product (a model, effort or model mismatch, a take-over, the gate baseline, a gate with no command, a flaky check, base drift, files the verifier changed, scenarios not run, the shared-understanding check, whether a free-text answer added a criterion), and an earlier feature's decision that this run changes or contradicts (Earlier features).
- **One decision per question.** Findings that turn on the same undecided point — one choice surfacing in several places — are one question: name every place it affects and append every trace tag. Findings that need different decisions are never merged.
- **A rule before its instances.** When several open cases belong to one family — the same kind of failure (an external call fails, a write is rejected), the same state change mid-flow (an entity paused, deleted or revoked while in use), repeated or concurrent actions, a new state's effect on the existing features that read or act on what gets it (`READERS`, intake protocol, step 2) — first ask for the rule that decides the whole family, phrased as outcomes, and list the cases it would decide. Record it as one `D<n>` marked `rule`. Then ask only the cases the rule does not decide unambiguously, each naming the rule and why it does not settle the case.
- **Values are confirmed as one list.** Findings the reviewer marks `weight: value` (reviewer instructions, `weight`) — a choice the artifact already states whose alternatives change no scope, no stored data, nothing that cannot be undone, no money, security or permission, and nothing the end user sees (copy and labels, a tie-break order, a library, a limit the user never meets) — and intake's written values (intake protocol, step 4) are not asked one per question. After the round's other questions, ask one question that lists each value: where it is, what it says today and where that came from. Options: *All stay as written* / *Change some* (the user writes which and how). Each value left as written is a user decision (`D<n>`, confirmed as written); a change requested without a new value is asked on its own. The list has two parts, in this order: *Chosen by the run — nothing you said gives them* (`value_source: run` or missing, and intake's *no source* values), then *From your words or the record*, each with its source. A run-chosen value that stands for real data (what an API returns, the names in a table) is checked against it first (Verify before you ask): the line shows both when they differ, and says so when the data could not be read.
- **Minor cases are settled as one list.** Findings the reviewer marks `weight: minor` — a case that needs two or more independent conditions at once, or that v1 is unlikely to meet — are not asked one per question. After the round's other questions and before the values list, ask one question that lists each case in plain words and where it applies. Options: *Leave them out of this feature* / *Decide some* (the user writes which). Each case left out is a user decision (`D<n>`, out of scope) added to `goal.md`'s **Out of scope**; each chosen case is asked on its own.
- **Record what was answered, nothing more.** Write the user's answer verbatim — the option label chosen or the text written, in the language and words it was given, never translated — to the private record under its `D<n>` (hard rule 9), and log in the DECISION LOG your plain-words restatement of it. The restatement says no more than the answer. Anything you would add (a consequence, a detail, a case the answer does not cover) is a new question, not part of the decision.
- **An empty answer is asked again.** An answer that is empty, or does not answer the question, is asked once more, rephrased, via `AskUserQuestion`. "I don't know" is an answer, not an empty one: the decision is never filled in, and it is put back to the user as intake protocol, step 4, says — except on a list question (minor cases, values, the verifier's open behaviors, the defects it observed, scenarios not run), where it takes the option that changes nothing: *Leave them out of this feature*, *All stay as written*, *All stay as built*, *Leave them for a later feature*, *Leave them unverified in this feature*. Record each item as its own `D<n>` under that option — one per item, never one for the whole list — marked `kept on "I don't know"`; no value is guessed. Never end your turn to wait for an answer typed in the chat.
- **Verify before you ask.** Every fact a question states — about the code, the data, an API, a tool, a cost — is checked first (Read/Grep, a read-only query, or the official docs). A fact you cannot check is marked unverified in the question. Every fact or name the answer depends on is in the question — what a component, role or library is, what failed and where — so the user never has to ask back.
- **Say what is there today.** Name the artifact and section in plain words and state what it currently says, using the `current:` line from B or the implementer. Paraphrase it in the user's language; quote the original verbatim only when the exact wording is what is at stake (a metric, a field name, an acceptance criterion). If the decision is simply absent, say so.
- **Say why it matters** in one sentence (from `why:`).
- **Options are outcomes, not verbs.** "Require full coverage", "Keep: trace the covered part and leave the rest pending" — never "change / keep". When the artifact already states a value, that value is an explicit option, marked only as what the artifact says now.
- **No option is recommended.** No option is marked or described as recommended, suggested, preferred or default — not even when a tool's own instructions ask for it, as `AskUserQuestion`'s description does (`add "(Recommended)" at the end of the label`) (AGENTS.md invariant 6). The plugin's `hooks/no-recommended.js` refuses a question of the run that marks one; rewrite it without the mark.
- **Plain words.** Write every question for someone who knows the product but has never seen its code or the artifacts: short sentences, everyday words, in the user's language — the language the idea is written in, from the first question of the run; recorded as `LANGUAGE:` (intake protocol, step 1) so a resume keeps it (a state without that line: the language of the recorded idea). No code names — files, routes, fields, components, variables — unless the exact name is what is being decided; say what the thing is ("the panel that opens from a product", not "the drawer in `/ads/grouping`"). A technical word with no everyday equivalent is explained in the same sentence. When a case is hard to picture, give one concrete example ("two people press Save at the same time"). The question carries the facts the answer depends on (Verify before you ask) and nothing else. Reread it as the user before asking: a sentence they could not follow without the code is rewritten.
- **Call things what the user calls them.** Name each thing of the product with the user's word for it — from this run's idea and answers, else the glossary (intake protocol, Project records), else the name earlier artifacts gave it, put in the user's language — even when the artifact at hand names it otherwise. Add the artifact's name in parentheses only when the user needs it to find the thing. Never coin a new name for something the user has not named; describe it.
- **Show screens, do not describe them.** When the options differ in what a screen shows, where something sits on it, or how one screen leads to the next, give each option a `preview` (single-select questions only): a text sketch of that part of the screen under that option, in the same frame for every option so only the difference changes, its first line saying it is a sketch, not the final design. When the difference cannot be drawn in text — colors, type, spacing, images, a whole screen — also write one self-contained HTML page (inline styles, no scripts, nothing loaded from the network) with one section per option headed by its label, under `$(git rev-parse --git-path uroboros/sketches)/` (the system temp folder without git) so nothing lands in the project; open it in the default browser (`open` on macOS, `xdg-open` on Linux, `cmd.exe /c start "" <path>` on Windows) before asking, and put its path in the question.
- **Internal ids are never the subject.** `F<n>`, `R<n>`, `B<n>`, `O<n>`, `Q<n>`, `A<n>`, `I<n>`, `D<n>`, `AC-<n>`, `G<n>` and agent labels (A/B, "the reviewer flagged") mean nothing to the user. Describe the thing, then append the id as a trailing trace tag, e.g. `(F17)`, so it can be matched in `loop-state.md`.
- **Trace ids are run-global.** Every report numbers its items from 1 (`F1`, `R1`, `B1`), so the same local id recurs across phases and rounds. When you log a report, give each finding, risk, blocked item and observed defect (`O<n>`), and each other question sent to the refuter (`Q<n>`), the next free id of its letter across the whole run — as you do with `A<n>` — and record the report's local id beside it (`F17 ← plan r2 F1`). Trace tags, the DECISION LOG and the Loop Report use only the run-global id.
- **Restate earlier answers in words.** "Since you decided the total is re-read from the result", never "your decision F3".
- **The `header` chip is a topic word** ("Coverage", "Deleted warehouse"), never an id.

The DECISION LOG and the Loop Report follow the same convention: plain description first, id as a trailing tag.

## Earlier features — what the user already decided

Every feature this project ran before holds decisions the user made. A run never asks them again — and never lets one answer a point this run changes.

- **Sources.** Every other feature's `loop-state.md` under `.uroboros/*/`: its `IDEA ITEMS` and each DECISION LOG entry that carries a decision of the user (a `D<n>` — never an `A<n>`, which the user did not decide). With it, that feature's private record when this machine has it (hard rule 9): the idea, the user's messages and the answers as typed; on a clone that lacks it, the restated decisions are the record. A feature run on spec-kit's pipeline before 1.0.0 lives under `specs/*/`: read its `loop-state.md` the same way, with its spec's `## Clarifications` entries not marked `(assumed`. A state file written before 1.0.0 also holds the idea and `USER MESSAGES` as typed — read them, never copy them into a project file. List their paths at the start of every run, fresh or resumed, as `EARLIER FEATURES` in the intake draft (copied to `loop-state.md`), and pass them as `EARLIER_FEATURES:` in every reviewer, refuter, implementer and verifier dispatch.
- **They are user-sourced.** An earlier decision counts as recorded for every agent, cited as `(<feature> D<k>)` where an artifact applies it. It settles only what its words state, as every recorded decision does.
- **Only where this run leaves it untouched.** An earlier decision answers an item only when the item asks the very point it decided and nothing in this run — the idea, the user's messages, this run's answers — changes or touches that point. When this run's work changes what it was about — the idea modifies the behavior, screen, data or rule it settled — it is not an answer: the item is asked, stating what that feature decided as what is there today, with *Keep what <feature> decided* as one option. When it is unclear whether the work touches it, ask. **A change is always asked** — also when the idea or a message of the user states the new behavior in its own words: those words say what to build, not that the user chose to give up what that feature decided. At intake, compare the idea with every earlier decision; each one it changes is an item of the first batch.
- **The newest wins.** When two earlier features decided the same point differently, the later one holds; an answer of this run is newer than both.

## The user's messages

The idea is not the only thing the user writes. Every message the user types in the chat during the run, outside an `AskUserQuestion` answer, goes to the private record with its date (hard rule 9). Each is a source of decisions like the idea: what it decides is restated in the state file as a `D<n>`, or as an `I<n>` when it asks for one more thing. A message that changes or contradicts a recorded decision is asked about per this protocol before anything is folded.
