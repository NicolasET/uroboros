# Contributing

Issues and PRs welcome. Coding agents working on this repo follow [AGENTS.md](./AGENTS.md) (purpose, invariants, change and release process). Ground rules:

1. **The zero-inference invariant is non-negotiable.** Any change that lets an agent silently assume a product/design decision will be rejected — that is the failure mode this project exists to eliminate.
2. **One definition, referenced at the point of use.** Define each rule completely in one place, and wherever the orchestrator executes it put a short reference to that definition (e.g. "round cap per step D") — never leave the point of use silent, since distant instructions get skipped under auto-advance momentum, and never copy the rule, since copies drift.
3. Keep the reviewer read-only and the output contracts (`LOOP-REVIEW-FINDINGS`, `IMPLEMENTER-REPORT`) stable — the orchestrator parses them. The role instructions live in `references/reviewer-instructions.md` and `references/implementer-instructions.md`; the `agents/*-<effort>.md` variants (low, medium, high, xhigh, max) differ only in `effort` and must stay thin pointers to them.
4. Test a change with a real spec-kit repo before opening the PR, and note in the PR which phase(s) you exercised. Every minor and major release is also measured by the maintainer with [uroboros-testbed](https://github.com/NicolasET/uroboros-testbed), a fixed scenario whose results are compared version to version.
5. **Model guides** (`references/model-guides/<family>-<version>.md`) are one file per exact release, distilled from that release's published guidance: frontmatter with `family`, `version`, `model_id`, `source` and `retrieved`, then `## Orchestrator`, `## Reviewer` and `## Implementer` sections. Carry only what the source says for that release — no guidance inferred to apply to other models — and nothing that overrides the Hard rules, the Question protocol, or the output contracts. A guide may change a role's behavior on its release — a reviewer threshold, an extra intake question — when its source says so; name every such change in the CHANGELOG entry and the README's Model guides bullet.
