# Changelog

## 0.22.0 — 2026-10-22

What the project remembers. `.uroboros/decisions.md` could only grow: the end-of-run offer could propose a decision an entry already stated, a run that set a standing decision aside left it binding for the next one, and nothing could be retired. Candidate rules had no check against what the constitution or `CLAUDE.md` already says, and could come from a failure of the machine rather than the project. And each run rediscovered the same technical facts — the gate commands, how to start the product, a setup trap.

- **Standing decisions: no copies, and a way out.** The Loop Report leaves out a decision an `S<n>` already states and offers *replace S<n> with …* instead of a second entry. In the same question it lists each standing decision the run set aside or contradicted, with what the run decided instead: *Keep them as they are* / *Change or retire some*. Retired entries move to `## Retired` with the run and the date; they are never deleted and no longer bind (reviewer and implementer read them so). Under `--auto`, both lists are shown for the user to apply by hand.
- **Candidate rules: general, justified, new.** Each candidate is one general rule with one sentence on why; the report reads the constitution and `CLAUDE.md` first and leaves out a rule they already state; an environment failure, a transient error or a dead end the run backed out of never becomes one.
- **Project notes.** New `.uroboros/project-notes.md` holds technical facts only — gate commands, `VERIFY COMMANDS`, setup traps, flaky tests — one line each: `- N<n> <fact> (seen <feature>, <date>; verified by <how>)`. Every run reads it; A2 and verify V1 consult it before rediscovering; each entry is verified again before it is relied on, and corrected or removed when it no longer holds. The run writes it at the end without a question, in every mode — facts, not decisions — and the Loop Report lists each entry added, changed or removed. Left uncommitted.
- **Contract change (additive):** `.uroboros/decisions.md` gains a `## Retired` section; new file `.uroboros/project-notes.md`.

## 0.21.0 — 2026-10-22

Long runs that are not lost. A run that outlives one session's context or one session — a compaction, a crash, a resume the next day — picked up from `loop-state.md`, but nothing told a compacted session to re-read it, a result recorded before files changed was trusted as is, a subagent whose report never arrived was neither waited for nor re-run, the branch the feature started from could move underneath it, and an SDD run had no marker, so two runs in one repository did not see each other.

- **One marker for both modes.** `.uroboros/active-run.json` gains `mode` (`sdd` | `goal`) and `state_file`; SDD writes it in Phase 0.5. One active run per repository: a run that finds another session's active marker asks before taking it over (*Take it over* / *Stop this run*; under `--auto`, taken over as an `A<n>`). A resume writes its session id; a `--goal` resume takes over only a goal marker. SDD sets `complete` or `stopped` when it ends.
- **The Stop hook keeps only goal runs alive.** `goal-gate.js` blocks only when `mode` is `goal`, or when a marker without `mode` carries `rounds_max` (written before 0.21.0); on any other doubt it allows the stop.
- **After compaction, back to the files.** New `hooks/resume-context.js`, a SessionStart hook on `compact` ([hooks](https://code.claude.com/docs/en/hooks.md)): for the session that owns the active run only, it adds the paths of the run command, the state file and, in goal mode, the goal protocol as context, to re-read before going on with the resume check. Otherwise it emits nothing.
- **Open dispatches and stale results.** Before every Agent call the orchestrator writes `DISPATCH OPEN` in `loop-state.md` and removes it when the report is read: on a resume, the same session keeps waiting for the notification, another session re-dispatches and never assumes the result. From implement on, every gate run, review and verification records the snapshot it ran on, and `LAST TREE` follows the latest of them and of each round's snapshot; a resume whose working tree differs asks verify V2's question before using anything recorded (under `--auto`, it stops and reports).
- **Base drift.** Phase 0.5 and goal G2 record `BASE BRANCH: <name> @ <sha>`. Before the first implementer dispatch and on every resume, `git log HEAD..<name>` on the local ref lists what the base gained — never a fetch, pull or rebase. If it touches a file the plan, tasks or `goal.md` names, or one the run changed, the user chooses *Continue on the current base* / *Stop so you can update the branch yourself* (under `--auto`, continue as an `A<n>`); the list goes to the implementer and the reviewer as `BASE DRIFT`.
- **Goal mode: Stop when, and criteria that appear mid-run.** `goal.md` gains a **Stop when** section, asked at intake (`none` is an answer, and "I don't know" records `none` rather than a deferred decision; under `--auto`, `none` as an `A<n>`). The implementer reports `stop_reached` when it meets one; that stops the run in every mode, never resolved by assumption. A free-text answer that asks for something no `AC-<n>` states is confirmed with one question and, if added, becomes the next `AC-<n>` with a `D<n>`, reviewed as a fold of `goal.md`.
- **Contract change (additive):** the marker gains `mode` and `state_file` and is written in SDD runs; `hooks/hooks.json` gains the SessionStart hook; `loop-state.md` gains `DISPATCH OPEN`, `LAST TREE` and `BASE BRANCH`; reviewer and implementer dispatches may carry `BASE DRIFT`; `goal.md` gains **Stop when**; `IMPLEMENTER-REPORT` gains `stop_reached`.
- **Testbed ([results/0.21.0+49bf109](https://github.com/NicolasET/uroboros-testbed/tree/main/results/0.21.0%2B49bf109), scenario v6, verifier eval v2, reviewer eval v1, against [0.20.0](https://github.com/NicolasET/uroboros-testbed/tree/main/results/0.20.0%2B716cc04)):** default 5/5 ambiguities, 11/11 hidden tests, 3/3 runtime, 14 questions (0.20.0: 5/5, 11/11, 3/3, 13); `--auto` 5/5, 8/11, 3/3 (same); `--goal` 5/5, 11/11, 3/3, 14 questions (12; one is the new Stop when); compat passes; verifier eval each defect 3/3, reviewer eval each defect 3/3, both clean copies clean (same). Every run closed its marker as `complete` and left no open dispatch. Cost: default −1%, `--auto` −6%, `--goal` +1%, compat +17% ($0.23 → $0.27), verifier eval +7%, reviewer eval −4%. The scenario never compacts, resumes or moves the base branch, so it shows the new records written and quality held, not the recovery paths taken. Default ran twice: in the first run, after verification, every tool call of the session failed with `Tool permission request failed: AbortError: Stream closed`; the orchestrator left the marker active and the verifier's dispatch open and told the user to resume, as this release asks. That run was discarded and default re-run; the result keeps the re-run.

## 0.20.0 — 2026-10-21

The verifier probes. The verifier ran the approved scenarios as written and never added one, so a rule the spec states but no Given/When/Then exercises — an error code, a refused action that must change nothing, a boundary — was checked only by the tests the implementer wrote for it.

- **Probes from the requirements.** After the scenarios, the verifier derives probes from the text — in SDD each FR and each edge case, error or invalid input the spec names; in goal mode each `AC-<n>` and constraint — one per behavior, refusal and boundary, compared exactly (status, body, error text, exit code). Scenarios stay as written: a probe never changes a scenario's outcome.
- **Invariants and the base.** After every refused action the verifier reads the data back; each item of `### Shared code touched`, and each out-of-scope surface a changed file reaches, is compared with the product as it was before the run: `BASE_TREE` extracted with `git archive` into a temporary directory outside the project and started there without installing anything or linking into the project. A base that does not start that way is recorded as not run.
- **What a probe finds.** A probe of an outcome the text fixes that fails is a gate failure, fixed like a failed scenario. A probe that fails the same way on the base is not this run's and is listed with what the verifier saw outside the feature. A probe whose outcome the text never fixed comes back as `open`: one list question, *All stay as built* / *Change some*; each answer is a `D<n>` (under `--auto`, an `A<n>`), and the next verification reads it as fixed.
- **Contract change (additive):** `VERIFIER-REPORT` gains `probes:` (`source`, `kind`, `expected`, `outcome`, `evidence`, `base`) and `open:`; the verifier dispatch gains `BASE_TREE`.
- **Testbed ([results/0.20.0+716cc04](https://github.com/NicolasET/uroboros-testbed/tree/main/results/0.20.0%2B716cc04), scenario v6, the new verifier eval v2, reviewer eval v1, against [0.19.0](https://github.com/NicolasET/uroboros-testbed/tree/main/results/0.19.0%2B35163f0) and, for the verifier eval, [0.19.0 on v2](https://github.com/NicolasET/uroboros-testbed/tree/main/results/0.19.0)):** default 5/5 ambiguities, 11/11 hidden tests, 3/3 runtime, 13 questions (0.19.0: 5/5, 11/11, 3/3, 11); `--auto` 5/5, 8/11, 3/3 (same); `--goal` 5/5, 11/11, 3/3, 12 questions (12); compat passes; reviewer eval each defect 3/3, clean copy clean (same). The pipeline runs' verifiers ran 8 to 12 probes each, none failed and none was left open. Verifier eval v2 adds FR-006 (an unknown listing id is refused with 404) and the `edge` case, whose server answers 403 where no scenario looks: caught 3/3 (0.19.0: 0/3); every other defect 3/3 and the clean copy without a failure (same); the clean copy left one to three behaviors open per run, all ones the spec does not fix (an unknown caller id, the error code of a refused caller). Cost: default +21%, `--auto` +11%, `--goal` +14%, compat −28%, reviewer eval +3%; verifier eval +39%, the probes' own work — above the +25% this series allows per mode, published on the maintainer's call.

## 0.19.0 — 2026-10-21

Evidence, not claims. A reviewer's `CLEAN` listed evidence per criterion, but nothing said whether the reviewer had checked it or was repeating the implementer's report; a new test counted as proof even if it would have passed without the feature; a report with a missing field or a criterion left out had no defined path; and the refuter could not dismiss a question the repository already answers. Ideas from [orca](https://github.com/stablyai/orca) (reviews that separate what was checked from what the lead reported; a pre-fix run that shows the new test fails), [hermes-agent](https://github.com/NousResearch/hermes-agent) (one bounded retry carrying only the missing fields) and [t3code](https://github.com/pingdotgg/t3code) ("do not ask questions that can be answered from the repo").

- **Evidence names its source.** Each `evidence` entry of `LOOP-REVIEW-FINDINGS` gains `source: artifact | gate | implementer`, cited as `file:line`, a test by file and title, or a gate output line. On implement and goal-implement, a criterion only the implementer vouches for is a `proof` finding: the fix adds the test or evidence, without a question. Step C's "satisfactory evidence" is defined by it.
- **Red first.** The implementer runs each test it writes for a behavior before the code that makes it pass and reports the failing line in a new `red_first` field, logged under `### Red first`. The reviewer cites it; without it, it reads the assertion and cites that. A test that would pass without the feature is a `proof` finding (rewrite it); a missing red-first line alone never is, so no round can loop on it.
- **Contract check, one repair.** After the Model check, every report is checked against its role's output block: missing block or field, `CLEAN` without evidence, evidence that leaves out a criterion (each FR/SC on implement, each `AC-<n>` in goal mode), a refuted item without `reason` or `proof`. A broken report is not used: it is repaired once, asking only for what is missing — through `SendMessage` to the same agent when the session has it ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents.md); not documented for headless or Agent SDK sessions), otherwise a fresh dispatch with a `REPAIR:` line — then dispatched fresh once more, then the run stops and reports. Every role accepts `REPAIR`.
- **The refuter's `discoverable`.** A finding that asks for a fact the repository already states is refuted with `reason: discoverable` and the citation; the orchestrator folds the fact where the finding pointed (through the implementer on implement) and the next round verifies it. Whether to use what exists stays a decision. When a finding turns on a fact with several candidates in the code, its options name the actual paths.
- **Contract change (additive):** `LOOP-REVIEW-FINDINGS` evidence gains `source`; `IMPLEMENTER-REPORT` gains `red_first`; `LOOP-REFUTER-RESULTS` `reason` gains `discoverable`; every dispatch may carry `REPAIR`; `loop-state.md` gains `### Red first` and the repair records.

The reviewer eval sits at 3/3, so it guards against a regression rather than showing the new checks catch more. Cost: default −20%, `--auto` −28%, `--goal` +2%, compat +19% ($0.27 → $0.32), verifier eval −9%, reviewer eval −2%. Earlier runs of this release: run 1 stopped `--goal` at the `goal.md` review, where the reviewer read the evidence rule as a demand that the design require tests; the rule now governs only the evidence a reviewer cites. ## 0.18.0 — 2026-10-21

What was asked, everywhere, and nothing more. The reviewer checked that the code did what the spec said; it did not check that the code did nothing else, that a behavior reachable from one screen or route was reachable from the others the user expects, or that the user's own words survived the English specify prompt. And a convergence task flagging unrequested code went to the implementer, which decided alone whether to keep it. Ideas from [t3code](https://github.com/pingdotgg/t3code) ("hit every surface", "a one-way door is a bug"), [hermes-agent](https://github.com/NousResearch/hermes-agent) ("nothing extra added") and [gentle-ai](https://github.com/Gentleman-Programming/gentle-ai) (user strings quoted verbatim; declare the shared code a change touches).

- **Unrequested changes are the user's call.** The implement review reports every behavior a user or client could observe that the run's diff adds — an endpoint, a flag, a response field, a UI state, a side effect — and every existing output or default it changes, when no requirement, task, plan item or decision is behind it: keep it or remove it. Silently ignoring an explicit input while reporting success is always reported.
- **Convergence `(unrequested)` tasks are asked.** `speckit-converge` marks code nothing called for as an `(unrequested)` task; it no longer goes to the implementer as is. *Keep it* records the decision in `spec.md`'s Clarifications, so the next converge pass reads it as intent instead of appending the task again; *Remove it* sends it to the implementer. The compat contract gains the converge marker `unrequested` (touchpoint 4).
- **Surfaces.** The intake's blind-spot pass lists where a behavior can be reached or seen — routes, CLI commands, UI entry points, jobs, roles, public and admin views, exports, docs — as `SURFACES`, and which of them the feature covers is asked as one rule. The specify prompt (and `goal.md`) carries them in and out of scope; the specify, plan and tasks reviews check each one is covered or out of scope; implement evidence names, per requirement, the surfaces where it is reachable.
- **The way back.** Every new state the idea creates (paused, hidden, archived, locked) needs a way out and a way for the user to see it: intake asks it, and the specify and goal reviews report a state without one.
- **Literals verbatim.** The specify prompt is English, but the user's exact strings, messages, labels, examples, commands and numbers now travel in a **Literals** section in their own language (`goal.md` too). The specify review folds a missing or reworded literal back from the intake answer without asking; the implement review reports code that renders one differently. AGENTS.md's "Prompts are English" rule names the exception.
- **Reuse, and the shared code a change touches.** The plan review asks each new component to name the existing mechanism it builds on and reports a duplicate as a risk. The implementer reuses the helper that already owns shared state and declares every piece of shared code it changed in a new `shared_touched` field, logged under `### Shared code touched` for the implement review's risk pass.
- **Testbed ([results/0.18.0+63471dd.dirty](https://github.com/NicolasET/uroboros-testbed/tree/main/results/0.18.0%2B63471dd.dirty), scenario v6, verifier eval v1, reviewer eval v1, against [0.17.0](https://github.com/NicolasET/uroboros-testbed/tree/main/results/0.17.0%2B94b45c4.dirty)):** default 5/5 ambiguities, 11/11 hidden tests, 3/3 runtime, 16 questions (0.17.0: same); `--auto` 5/5, 8/11, 3/3 (same); `--goal` 5/5, 11/11, 3/3, 10 questions (14); compat passes; verifier eval each defect 3/3 and reviewer eval each defect 3/3, both clean copies clean (same). The scenario's feature has one surface family and no unrequested code, so it shows quality held, not the new checks catching. Cost: default +1%, `--goal` −3%, reviewer eval +1%; `--auto` +22% — its specify and tasks reviews each raised one finding (error codes, a task-order contradiction), adding two refuter dispatches and a tasks round. The verifier eval was re-run once: in the first run the harness missed one report the verifier had wrapped in a four-backtick fence; the harness now reads any fence width.
- **Contract change (additive):** `IMPLEMENTER-REPORT` gains `shared_touched`; `loop-state.md` and the intake draft gain `SURFACES` and `### Shared code touched`; the specify prompt and `goal.md` gain `Literals` and the surfaces in and out of scope; `spec-kit-compat.json` adds the converge marker `unrequested`.

## 0.17.0 — 2026-10-21

The gate measures only this run. Implement judged "the changed files" from `git diff`, which mixed in whatever the user had uncommitted before the run and, until 0.16.2, missed new files; the reviewer saw a file list but never a diff, so a weakened check — a skipped test, a loosened assertion, a suppressed type error — was invisible unless it read every line; and a project whose suite was already red burned review rounds on failures the run did not cause. Ideas from [orca](https://github.com/stablyai/orca) (baseline ratchets, evidence of what a review actually checked), [hermes-agent](https://github.com/NousResearch/hermes-agent) and [gentle-ai](https://github.com/Gentleman-Programming/gentle-ai) (only new failures block), and [t3code](https://github.com/pingdotgg/t3code) (checkpoints that never touch the user's branch or index; suppressions need a reason).

- **Working-tree snapshots.** Before the first implementer dispatch the orchestrator records `BASE TREE`, and after each dispatch `ROUND TREE <n>`: git tree ids of every non-ignored file, untracked ones included, written through a temporary index inside `.git` — no commit, no ref, the user's index untouched. The run's diff is `BASE..ROUND`, so edits the user had before the run never count as the run's and new files are never missed. Defined once in the orchestrator (`Working-tree snapshots`); goal mode, the verify protocol and the Loop Report refer to it. Without git, or when a recorded tree has been pruned, the run falls back to the 0.16.2 changed-file list and says so.
- **The reviewer and the refuter read the diff.** They cannot run git, so the orchestrator writes the run's unified diff to `.git/uroboros/run.diff` and passes it as `RUN_DIFF`; from round 2 the last fold's diff arrives as `FOLD_DIFF`.
- **Gate baseline.** The gate commands run once on the untouched tree before any code is written (`GATE BASELINE`). If the suite is already red, one question: fix those failures in this feature, leave them out of this run's gate, or stop — asked under `--only-business` too, since it changes what the feature covers. Under `--auto` they are left out as `baseline — red` assumptions, listed in the Loop Report's ledger right after `skipped — red`. Hard rule 5 now names both exceptions.
- **Gate integrity.** The implementer never turns the gate green by weakening it (suppressions, `.skip`/`.only`, deleted or loosened assertions, relaxed configuration or thresholds, longer timeouts) and declares every existing check it touched in a new `gate_touched` field, logged under `### Gate touched`. The implement review reads `RUN_DIFF` for those patterns against that list.
- **`weight: proof`.** A gap in the evidence with one fix and no decision in it — a weakened check to restore — is fixed through the implementer like a red gate: never asked, no refuter, reported in later rounds too, `skipped — red` if it repeats under `--auto`, and never "left out" at an exhausted cap. Implement and goal-implement only.
- **The refuter says why, and knows what the run did not cause.** `LOOP-REFUTER-RESULTS` gains `reason: decided | unreachable | no-outcome | not-this-run`. The new `not-this-run` refutes a finding about behavior that was already there before the run (outside `RUN_DIFF`) and that nothing asks to change; such items go to the Loop Report's section *Seen outside this feature* (formerly *Seen while verifying, outside this feature*), next to what the verifier observed.
- **Verification compares trees.** V2 compares the snapshot before and after the verifier: a modified or deleted file is asked about as before; added files go to the Loop Report.
- **Testbed ([results/0.17.0+94b45c4.dirty](https://github.com/NicolasET/uroboros-testbed/tree/main/results/0.17.0%2B94b45c4.dirty), scenario v6, verifier eval v1 and the new reviewer eval v1, against [0.16.0](https://github.com/NicolasET/uroboros-testbed/tree/main/results/0.16.0%2B243c7ba.dirty) and, for the reviewer eval, [0.16.2](https://github.com/NicolasET/uroboros-testbed/tree/main/results/0.16.2)):** default 5/5 ambiguities, 11/11 hidden tests, 3/3 runtime (0.16.0: 5/5, 11/11, 3/3), 16 questions (14); `--auto` 5/5, 8/11, 3/3 (same); `--goal` 5/5, 11/11, 3/3, 14 questions (11); compat passes; verifier eval unchanged (each defect 3/3, no false failure). The new reviewer eval plants five defects that keep the gate green in the reference implementation: the suppressed type error is now caught 3/3 (0.16.2: 1/3, 0.16.1: 2/3 — without a diff the reviewer dismissed the `@ts-expect-error` as already there), every other defect 3/3 as before, and the clean copy returns CLEAN 3/3. Cost: default +3%, `--auto` +3%, reviewer eval −14%. `--goal` ran twice: $2.94 (+26% — its `goal.md` review took three rounds and a refuter, a phase this release does not change) and $2.69 (+15%) on the re-run the result keeps.

## 0.16.2 — 2026-10-20

- **The implement reviewer sees new files.** Its changed-file list came from `git diff --name-only`, which omits untracked files, so a file the implementer created was never in the list it audited; the verifier's list already added them. The changed-file list is now defined once, in the reviewer dispatch (step B), as `git diff --name-only` plus `git ls-files --others --exclude-standard`, and goal mode and the verify protocol refer to it.
- **A coherence check for the repo.** `scripts/check-coherence.js` (Node standard library) derives its rules from the files themselves: every cited `references/`, `agents/`, `hooks/`, `skills/` and `scripts/` path exists; the effort variants of each agent differ only in name, description effort and `effort`; every `key: value` a prompt cites for a report key with an enum uses one of its values; JSON parses; hooks pass `node --check`; the spec-kit snapshot hashes match; the compat `.md` states the `.json`'s baseline and range; the manifest version is the latest CHANGELOG section; every flag is in the argument hint and the README. AGENTS.md step 5 now runs it. Ideas from [orca](https://github.com/stablyai/orca)'s prompt-contract tests.

## 0.16.0 — 2026-10-17

The product used, not only tested. Until now a run closed on the reviewer's `CLEAN` and a green test/lint/typecheck gate, and the tests were written by the same implementer they judged: nothing ever used what was built. Spec-kit's plan already writes `quickstart.md` as runnable validation scenarios, and the spec states each user story's acceptance scenarios; no step ran them. Anthropic's [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/) gives the same advice: give Claude something it can run and have it show the output.

- **A verifier closes implement and goal mode.** New `uroboros-verifier-<effort>` variants start the product, call its API or CLI and drive its UI, scenario by scenario: each acceptance scenario of the spec and each `quickstart.md` scenario (goal mode: each `AC-<n>`), as written, with evidence. It never edits the project; the orchestrator compares `git status` before and after, and asks about any tracked file that changed.
- **A failed scenario is a red gate.** The implementer fixes it; the gate, the review, the convergence gate and the verification run again, within the round cap. Under `--auto`, a scenario that fails the same way twice is dropped like any gate check (`skipped — red`).
- **Browser:** Claude in Chrome when connected, else the Claude desktop app's built-in browser, driven by accessibility refs; with neither, the run asks once whether to connect one or leave the UI unverified.
- **Local only.** Local development hosts, processes the verifier started and the project's test data. A scenario that needs an external service, real credentials or an outcome its text leaves open is reported as not verified, with the reason, at the top of the Loop Report's verification section.
- **Outside the scenarios.** Anything broken the verifier sees that no scenario covers is listed in the Loop Report, saying whether it touches a file the run changed; the run does not fix it.
- **One name per gate.** "Verification gate" meant the test/lint/typecheck gate; it is now "the gate (tests/lint/typecheck)" everywhere, and "verification" names only the verifier's step. The goal-mode Stop hook's relaunch message says the goal is met on CLEAN + green gate + verification passed.
- **Every task stays the implementer's.** In the testbed's first `--auto` run of this release, the implementer read that a verifier would follow and left the task "run quickstart.md" unchecked for it; the implementer instructions now say the verifier is an independent check, never a substitute for a task.

Reviews that converge. The maintainer's 18 full-pipeline runs since 0.14.0 asked about 112 questions each (every question in an `AskUserQuestion` call, model/effort and approvals included). - **Sweep before re-review.** After folding, the orchestrator brings every mention of each changed concept in line across the feature's artifacts; on implement, the implementer does the same in code and tests.

Fewer questions, still none assumed. The maintainer's last 25 non-`--auto` runs on three projects asked about 62 questions each on average (about 65–100 in default mode, 38–59 under `--only-business`; counted from the recorded decisions in each `loop-state.md`, so estimates). Every change below cuts questions without turning any into an assumption: each decision still comes from the user.

- **One question per decision.** Findings that turn on the same undecided point are asked once, naming every place it affects; the reviewer reports such a point once, with every place in `location` (separated by `;`). The same applies to `BLOCKED` items from the implementer.
- **A rule before its instances.** When several open cases belong to one family (the same kind of failure, the same state change mid-flow, repeated or concurrent actions), the user is asked the rule for the family first, recorded as a `D<n>` marked `rule`; only the cases the rule does not decide unambiguously are asked. Applies at intake and when relaying findings; the reviewer treats a case a recorded rule decides as sourced.
- **Standing decisions: `.uroboros/decisions.md`.** Product and behavior decisions the user makes binding for the project. Read at the start of every run and passed to the reviewer and implementer as `STANDING_DECISIONS`; never asked again; a contradiction is asked (keep, set aside for this feature, or change for the project). The Loop Report offers this run's candidates in one question; under `--auto` it only lists them.
- **Derived findings are folded, not asked.** A finding whose only consistent answer follows from a recorded decision carries `derived_from:`; the orchestrator checks that no other answer is consistent, folds it citing the decision, and the next review round verifies it. If another answer is consistent, it is asked as before.
- **Minor values are confirmed as one list.** The reviewer marks each finding `weight: decision | value`; `value` covers a single executor-written value whose alternatives change no scope, data, flow or failure behavior (copy and labels, a tie-break order, a cosmetic style), and `decision` is the default when unsure. Each round's `value` findings arrive as one question listing them, *All stay as written* / *Change some*; values left as written are recorded as user decisions.
- **Verify before you ask.** Every fact a question states — about the code, the data, an API, a tool, a cost — is checked first; one that cannot be checked is marked unverified. In those runs, about 5–9% of the questions were re-asks or follow-ups caused by a false premise or by the orchestrator's own folds.
- **The approved prompt is shown in full.** The specify prompt, and `goal.md` in goal mode, is shown verbatim for approval, never as a description of it. Merging the shared-understanding check into that approval was tried for this release and dropped: in the testbed the long merged text was approved with an unasked inference that the short summary had caught in every earlier run.
- **Decisions are recorded as answered.** Each decision is logged with the user's verbatim answer beside its restatement, and the restatement says no more than the answer; anything more is a new question. The reviewer flags a decision or artifact text that extends past the recorded answer. A testbed run of this release's candidate showed the gap: the answer "hidden from search" was logged as "hidden from search, and on resume it returns to the position its ranking gives it", and the extension was never asked.
- **An empty answer is asked again.** An empty answer, or one that does not answer the question, is asked once more, rephrased; "I don't know" stays a valid answer and is deferred as before. The run never ends its turn to wait for a typed reply. In the same testbed run, an empty answer to a follow-up question ended the run during intake.

## 0.7.1 — 2026-09-02

- **Self-contained questions (Question protocol).** Questions relayed to the user leaned on internal ids — "F17 and F20: confirm both?", "given your decision F3" — that exist only in the reviewer's report and `loop-state.md`, which the user never sees. A new Question protocol in the orchestrator (plus hard rule 8) now governs every `AskUserQuestion` of the run: one decision per question; state what the artifact says today (paraphrased in the user's language, quoted verbatim only when the exact wording is at stake) and why it matters; options phrased as outcomes, with the current value as an explicit option; internal ids (`F<n>`, `R<n>`, `B<n>`, `A<n>`, `FR-`, `SC-`, `US<n>`, `T<n>`) and agent labels never as the subject, only as a trailing trace tag; earlier answers restated in words; the `header` chip a topic word. Applies to intake, findings/risks, `BLOCKED` relays, the round-cap notice, goal mode, the DECISION LOG, and the Loop Report.
- **Reviewer and implementer report `current:`.** Each reviewer finding and each implementer `blocked_on` item now carries a `current:` line (what the artifact or code says there today, 1–2 lines, or `absent`), so the orchestrator writes the question from the report instead of from its own — possibly compacted — memory of the artifact.

## 0.7.0 — 2026-08-06

- **Goal mode (`--goal`).** A new flag that replaces the SDD pipeline with a completion condition, in the spirit of Claude Code's `/goal` — for small tasks where full SDD is overkill, and for repos without spec-kit (no `speckit-*` skill is invoked). Intake is unchanged but produces a `goal.md` (measurable condition + numbered `AC-<n>` acceptance criteria + constraints) that the reviewer audits before any code; the run then loops implementer → real gate → reviewer until CLEAN-with-evidence-per-criterion + green gate, capped by `--rounds`. Orthogonal to the question flags (`--auto`/`--only-business`) and the model flags. Protocol lives in `references/goal-protocol.md` (progressive disclosure — read only when the flag is present).
- **Stop hook keeps goal runs alive.** The plugin now ships `hooks/goal-gate.js` (Node), a Stop hook replicating `/goal`'s turn-relaunching: while `.uroboros/active-run.json` records an `"active"` goal run, ending a turn blocks the stop and resumes the loop from `loop-state.md`; the hook enforces its own relaunch cap (`--rounds`) and allows the stop on any doubt. Inert in non-goal sessions (marker absent → immediate allow).
- **Goal-mode state lives in `.uroboros/<slug>/`** (`goal.md` + `loop-state.md`, plus the transient `active-run.json` marker at `.uroboros/`), independent of spec-kit's feature directories. Branching uses plain git (`goal/<slug>`), not `speckit-git-feature`.
- Reviewer gained `goal` and `goal-implement` phase profiles (evidence per acceptance criterion); implementer accepts `GOAL_FILE` in place of spec/plan/tasks and reports `AC-<n>` ids.

## 0.6.0 — 2026-07-29

## 0.5.0 — 2026-07-24

Context-engineering pass following Anthropic's Claude 5 guidance (judgement over repetition, progressive disclosure, surfacing unknowns).

- **Blind-spot pass at intake.** Before interrogating, the orchestrator explores the codebase around the idea and surfaces the user's unknown unknowns — prior work in the area, invariants the idea touches, decisions it silently implies — and turns them into intake questions.
- **Questions ordered by impact.** Intake questions and relayed findings whose answer would change the architecture or data model come first; the reviewer now orders its findings most-consequential first.
- **References invited at intake.** The orchestrator actively asks for existing code, mockups, or libraries close to what the user wants, reads them, and carries them into the specify prompt — source code is the highest-fidelity spec input.
- **Deviations persist.** Every deviation the implementer reports in `notes` is appended to `loop-state.md` under the phase's `### Deviations`, and the Loop Report mines deviations (not just findings) for candidate rules.
- **Progressive disclosure.** The implement protocol and the Loop Report format moved out of the command into `references/implement-protocol.md` and `references/loop-report.md`, read only when their phase arrives.
- **De-duplicated command prompt.** The model/effort question rules, foreground-dispatch rule, and explicit-model rule now live in one Model/effort protocol section instead of being restated per phase.

## 0.4.0 — 2026-07-11

Audit the premises, not just the conclusions.
